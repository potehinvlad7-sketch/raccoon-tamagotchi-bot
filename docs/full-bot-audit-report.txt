1. ОБЩАЯ АРХИТЕКТУРА БОТА
Проект: Telegram RPG Tamagotchi с енотом-питомцем.
Точка входа: main.py -> asyncio.run(main()) -> Bot + Dispatcher -> register_handlers(dp) -> polling.
Aiogram: используется aiogram v3-подход с Router, фильтрами F, FSM (создание питомца, рассылка админа), CallbackQuery/Message split.
Routers:
- handlers/start.py: onboarding и создание питомца.
- handlers/menu.py: основной gameplay (статус, уход, инвентарь, магазин, путешествия, бой, магия/меч, помощь, письмо админу, уведомления low-needs).
- handlers/admin.py: админ-панель, пользователи, правки, backup, рассылка, контроль уведомлений.
Proxy: main.py читает PROXY_URL из config.py, при наличии создает AiohttpSession(proxy=PROXY_URL).
ENV: config.py load_dotenv(); BOT_TOKEN, PROXY_URL, ADMIN_IDS; BOT_TOKEN обязателен (RuntimeError, если пустой).
Хранилище: storage.py, JSON-файлы data/users.json и data/notifications.json. Без БД.
Runtime flow:
- Пользователь пишет /start -> либо возврат в меню, либо FSM создания питомца.
- Любая игровая ветка берет user/pet через storage, вызывает touch_user_needs/recalculate.
- Потребности изменяются событиями ухода/путешествия/боя/тренировок.
- Большинство UI-веток в handlers/menu.py.
Где живет логика:
- Сильный монолит storage.py: доменная модель, формулы, travel/battle/economy/inventory/уведомления.
- Сильный монолит handlers/menu.py: presentation + orchestration + часть fallback-логики.

2. ПОЛНАЯ КАРТА ФАЙЛОВ
main.py
- Назначение: bootstrap бота, запуск polling.
- Ключи: BOT_TOKEN/PROXY_URL.
- Риски: минимум; корректный простой entrypoint.
- Монолитность: нет.
config.py
- Назначение: env-конфиг и парсинг ADMIN_IDS.
- Ключи: BOT_TOKEN, PROXY_URL, ADMIN_IDS, is_admin().
- Риски: тихий пропуск невалидных admin id (дизайн-решение), может скрыть опечатки.
- Монолитность: нет.
storage.py
- Назначение: модель данных и практически вся игровая механика.
- Ключи: DEFAULT_NEEDS, DEFAULT_INVENTORY, DEFAULT_SKILLS, TRAVEL_LOCATIONS (100 локаций), TRAVEL_EVENTS, ENEMY_CATALOG, LOCATION_ENEMIES, ITEM_CATALOG, SHOP_*.
- Ключевые функции: create_pet, touch_user_needs/recalculate_needs, update_pet_mood, get_pet_status_phrase, update_pet_need, train_skill, perform_travel, resolve_battle_attack, resolve_battle_run, shop_purchase, notification log API, admin mutate API.
- Риски: очень большой файл, высокая связность, риск регрессий и drift в данных.
- Монолитность: критически высокая.
keyboards.py
- Назначение: все Reply/Inline клавиатуры и кнопочные константы.
- Риски: дублирование TRAVEL_LOCATIONS (вторая карта, урезанная) относительно storage.py.
- Монолитность: средняя.
handlers/__init__.py
- Назначение: регистрация роутеров.
- Порядок: start -> admin -> menu.
handlers/start.py
- Назначение: /start и FSM создания питомца.
- Риски: низкие.
handlers/menu.py
- Назначение: почти весь пользовательский UX + callbacks + бои/магазин/travel + уведомления.
- Ключи: локализации настроения/рисков, map кнопок/категорий, текстовые генераторы экранов.
- Риски: очень высокая длина и плотность; mix Reply+Inline UX.
- Монолитность: критически высокая.
handlers/admin.py
- Назначение: админка (статистика, users paging, edit pet, инвентарь/монеты, backup, рассылка, уведомления).
- Риски: много callback-веток в одной функции admin_callbacks, частично broad except.
handlers/images.py
- Назначение: send_optional_screen (картинка + caption, fallback на text).
- Риски: silent except TelegramAPIError -> pass (теряется причина).
README.md
- Назначение: описание проекта, запуск, stages, high-level features.
- Риск: частично не полностью синхронен с текущим кодом (например battle/travel глубже, чем кратко описано).
requirements.txt
- aiogram, python-dotenv, aiohttp-socks.
existing docs
- docs/audit-current-state.md: предыдущий аудит, подтверждает проблемы монолитности/дублирования.

3. ПОЛНАЯ КАРТА ПОЛЬЗОВАТЕЛЬСКИХ ЭКРАНОВ
/start: стартовый onboarding. Если pet есть -> главное меню; иначе выбор пола.
Создание питомца: ReplyKeyboard (♂️/♀️), затем ввод имени текстом.
Главное меню: ReplyKeyboard, кнопки статус/магия и меч/тренировки/путешествие/магазин/инвентарь/мой енот/помощь/письмо.
Статус: screen key status/pet-care (через send_optional_screen + inline care keyboard). Показывает фразу енота, шкалы, риск побега.
Мой енот/профиль: детальная карточка с уровнем/опытом/навыками/потребностями.
Инвентарь: развернутые категории + монеты + свитки.
Магазин: category ReplyKeyboard -> категория -> Inline buy buttons.
Путешествие: ReplyKeyboard с окном из 3 доступных локаций (по уровню).
Бой: ReplyKeyboard (Атаковать/Сбежать).
Магия и меч: отправка/редактирование inline-экрана с submenu training/potions/magic placeholder/skills.
Тренировки: inline magic_train:* + legacy reply training buttons тоже присутствуют.
Зелья: inline magic_potion:*.
Magic placeholder: "Этот раздел откроется позже." + back callback.
Навыки: отдельный inline-экран.
Письмо: FSM-like state ожидания текста, пересылка админу(ам).
Помощь: текстовый экран подсказок.
No-pet поведение: почти везде guard "У тебя пока нет енота. Нажми /start...".

6. ВСЕ ПОЛЬЗОВАТЕЛЬСКИЕ ФРАЗЫ И ТЕКСТЫ
Группы реализованы в коде:
- start/create: привет, выбор пола, ввод имени, ошибки пустого имени.
- main menu/help/profile/status/inventory/travel/battle/shop/training/potions/magic placeholder/skills/admin.
- mood labels: excellent/content/calm/tired/hungry/dirty/sad/anxious/critical локализуются MOOD_MAP.
- raccoon phrases: storage.py get_pet_status_phrase(), наборы hunger/clean/love/energy/good/adventure.
- low-needs notifications: отдельные тексты, есть special-case low_energy.
- errors/guards: нет питомца, нет предмета, недостаточно монет, категория недоступна и т.д.
Типы: часть статические, часть детерминированно-псевдослучайные (индекс фразы от seed), часть действительно случайные (GROUP_FLAVOR_LINES).

7. МОДЕЛЬ ДАННЫХ ПОЛЬЗОВАТЕЛЯ И ПИТОМЦА
По storage.py и ensure defaults:
user: id(str key в JSON), username, first_name, last_seen_at/metadata-поля.
pet:
- base: name, gender, level, exp, currency, mood
- needs: satiety, cleanliness, love, energy
- inventory: dict item_id->int
- skills: strength, agility, instinct
- timestamps: created_at, updated_at, last_need_tick_at, last_sleep_at, last_low_needs_notification_at
- travel: total_travels, last_event, optional current_location
- battle: None или dict (enemy_id/location_id/win_chance/travel_context...)
- flags: level_up_blocked и др. служебные в travel/boss flow.
Миграции: ensure_* функции добивают недостающие поля, исправляют невалидные типы.

8. СИСТЕМА ПОТРЕБНОСТЕЙ И НАСТРОЕНИЯ
- tick: NEEDS_TICK_MINUTES=30.
- recalculate_needs/touch_user_needs: вычисляет ticks по timestamp.
- decay/regen за тик: satiety -2, cleanliness -1, love -1, energy +3; clamp по max уровня.
- max needs: get_max_need_value/get_pet_max_needs (масштаб с уровнем).
- mood: update_pet_mood(), пороги по критичным/низким needs.
- фразы: get_pet_status_phrase(), выбор по lowest need/overall state.
- статус-бары: _need_bar/_need_block в handlers/menu.py.

9. БЫСТРЫЙ УХОД НА СТАТУСЕ
Inline callbacks:
- pet_care:feed -> берет первый доступный item из category food
- pet_care:clean -> category cleanliness
- pet_care:play -> category love
- pet_care:sleep -> sleep_pet (cooldown SLEEP_COOLDOWN 24h)
- pet_care:menu -> возврат в главное меню
Если предметов нет -> текст о нехватке и магазин.
Update экрана: _refresh_pet_care_card пытается edit_caption/edit_text, fallback -> answer.

12. СВИТКИ
Существуют: strength_scroll, agility_scroll, instinct_scroll.
Где живут:
- DEFAULT_INVENTORY: да
- ITEM_CATALOG: нет
- TRAVEL_EVENTS rare: да
- battle drop (win): может случайно дропнуть scroll
- admin add: да (admin:inv_add)
- shop: не продаются (SHOP_ITEMS не содержит scroll)
Потребление: train_skill() 1 scroll на тренировку соответствующего навыка.
Без свитка: train_skill -> fail + scroll_key для текста.
Риск: частичная «разъединенность» со стандартным item-каталогом (нет единого источника правды).

13. ТРЕНИРОВКИ
Навыки: strength/agility/instinct default 0.
Стоимость: энергия 15 + 1 соответствующий свиток.
Награда: +1 к навыку + EXP (через add_exp в train_skill).
Кнопки: inline magic_train:* и legacy reply BTN_TRAIN_*.
No-scroll/no-energy: отдельные тексты.
Влияние на бой/travel: расчет win chance/flee/drop scaling uses skills, особенно instinct.

14. МАГИЯ И МЕЧ
Кнопка в меню открывает гибридный flow.
Inline submenu: тренировки/зелья/магия/навыки.
Реально реализовано: training, potions, skills.
Placeholder: magic раздел с текстом "откроется позже".
Back: magic_*:back/main callbacks, чаще edit current message.

15. ЗЕЛЬЯ
IDs: energy_potion, big_energy_potion.
Effects: +50/+100 energy.
Использование: из care reply и из inline potion menu.
Покупка: в магазине категория potions.

16. МАГАЗИН
Категории, реально отдаваемые get_shop_categories(): food, household, toys, potions.
Плейсхолдер-категории в map UI: weapons/armor/accessories/materials (в кнопочной map есть, но не выдаются в реальном списке категорий).
Покупка: shop_buy:item -> shop_purchase (проверка валюты, списание, +1 item).
Риск: mismatch между потенциальными категориями и реально доступными.

17. ПУТЕШЕСТВИЯ
Данные локаций: storage.TRAVEL_LOCATIONS (100 уровней).
Дублирование: keyboards.TRAVEL_LOCATIONS содержит параллельную карту (без costs/rewards), риск рассинхронизации.
Окно доступа: показываются ~3 локации вокруг текущего уровня.
Расходы/награды: per-location costs/rewards + event effects.
События: good/neutral/bad/rare/enemy/boss gating.
Переход в бой: если event type enemy -> battle state + экран боя.
No-pet/no-energy/insufficient needs handled текстом.

18. БОИ
Старт: из travel enemy event.
battle state: enemy_id, location_id, win_chance, travel_context.
Атака: resolve_battle_attack, win probability clamp 15..90.
Победа: exp/currency + возможный item drop + возможно scroll drop + boss unlock logic.
Поражение: penalties needs.
Побег: resolve_battle_run, flee chance = 55 + agility*3 + instinct - difficulty*7 (clamp 20..90).
Cleanup: pet['battle']=None в attack/run resolve.

19. ЭКОНОМИКА
coins=pet.currency.
Доход: travel base rewards + event currency + battle win reward.
Расход: shop purchase.
Admin edits: +10/+50/+100/-10 или +100 money в pet edit.
Баланс-риски: высокие late-game награды и частые покупки дешевых предметов требуют тестов экономической кривой.

23. REPLYKEYBOARD VS INLINEKEYBOARD
Reply: глобальная навигация, travel выбор, battle reply, legacy training/care.
Inline: быстрый уход, magic&sword submenu, shop buy, админ-панель.
Смешанный UX риск: пользователь прыгает между edit-in-place inline и новыми сообщениями reply.
